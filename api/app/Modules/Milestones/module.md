## Purpose
Keeps the dates that matter - anniversary, first date, birthdays - and turns them into yearly planner events automatically, plus the 'days together' counter the couple will check far more often than they admit.

## User stories
- As a couple, we can set our anniversary and see it counting down.
- As a couple, we see how many days we have been together.
- As a couple, our anniversary appears in the planner every year without us adding it.
- As a partner, I get a reminder before my partner's birthday.

## Data model
**milestones** - id, couple_id, kind (`anniversary`|`first_date`|`birthday`|`custom`), subject_user_id (nullable - whose birthday), title, on_date (the original date), recurs_yearly (bool), created_by_user_id.

Generated planner events carry `source = milestone`, `source_id = milestone.id`, so regeneration is idempotent.

## API endpoints
| Method | Path | Auth | Purpose | Request | Response resource |

| GET | /api/milestones | sanctum | All milestones + computed counters | - | MilestoneResource collection |
| POST | /api/milestones | sanctum | Add a milestone | StoreMilestoneRequest | MilestoneResource |
| PATCH | /api/milestones/{id} | sanctum | Update a milestone | UpdateMilestoneRequest | MilestoneResource |
| DELETE | /api/milestones/{id} | sanctum | Remove a milestone | - | 204 |

## Business rules
1. Setting `couples.anniversary_on` or `first_date_on` creates the matching milestone, and vice versa - they must never disagree.
2. **Yearly events are generated for the next 12 months only**, and are regenerated by a scheduled command. Generating decades of rows ahead is waste.
3. Generation is **idempotent** on (milestone_id, year): running it twice creates nothing extra.
4. **'Days together' counts from `first_date_on` if set, otherwise `anniversary_on`, otherwise `linked_at`** - and the card says which, so the number is never mysterious.
5. A birthday milestone is linked to a user. If that user leaves the couple, their birthday milestone goes with them.
6. A 29 February anniversary is observed on 28 February in non-leap years.
7. Milestone reminders default to a longer lead time than ordinary events (7 days), because they usually need buying something.
8. Either partner may add or edit milestones.

## AI usage (if any)
None. Dates are arithmetic.

## Jobs, events & schedules
**Jobs:** `GenerateMilestoneEvents` (per milestone, next 12 months, idempotent).

**Events:** `MilestoneCreated|Updated|Deleted`; listens for `CoupleLinked` to seed an anniversary milestone from the linking date.

**Scheduled:** `milestones:generate` daily - tops up the rolling 12-month window.

**Emails (Resend):** milestone reminder, via the Reminders module.

## Mobile
**Screens:** Milestones list and editor inside the Us tab; the 'days together' and next-milestone countdown cards appear on Home and at the top of Planner.

**Components:** `Card`, `Sheet`, countdown display, `Button`.

**Navigation:** Us tab -> Milestones; surfaced on Home and Planner.

**Offline:** counters compute locally from cached dates, so they are correct with no network at all.

**Local notifications:** via Reminders.

## Permissions & privacy
`MilestonePolicy` - both partners may manage. A birthday is shared within the couple by definition once added; `users.date_of_birth` is not exposed until the user adds the milestone.

## Tests
`api/tests/Feature/Milestones/` and `tests/Unit/Milestones/` - yearly generation is idempotent; the 12-month rolling window; 'days together' source precedence; 29 February observation; milestone removal when a partner leaves; anniversary stays in sync with the couple record.

Run: `composer test -- --filter=Milestones`
